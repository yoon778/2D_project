## 1. 목표와 현재 상태

목표는 지도 1개·좀비 1마리·야구방망이 1종·택배 배달 1건을 끝까지 플레이하는 기본판
성공·체력 소진 실패·결과 화면 재시작까지 연결
2.5D 전환에도 걷기·좀비 90px/s, 달리기 135px/s, 스태미나 100·초당 25 소모·20 회복, 좀비 5타·제자리 0.4초 경직, 지면 빛 340px·80도를 유지
총기는 추가하지 않음

확정 방향:
- 정수리만 보이는 수직 탑뷰를 폐기하고, 앞·옆·등과 다리가 보이는 고정 사선 3/4 2.5D로 전환
- Python/pico2d의 2D 지면 좌표·충돌·소음·추격을 유지하고, 세워 그린 스프라이트로 시점 표현
- 왼손은 몸 앞의 택배, 오른손은 방망이, 가슴 부착등 유지
- 마우스 조준과 WASD 이동 분리
- 손전등 밖은 완전 암흑, 건물 윤곽만 희미하게 표시
- 보이지 않는 좀비 소리는 들리고, 공격 소음은 좀비의 조사 대상
- 실제 3D 엔진·Blender·z축 높이·발판 상자·옥상은 도입하지 않음
- 참고 그림은 분위기와 시점의 기준이며, 그림의 가방을 인벤토리 기능으로 추가하지 않음

구 탑뷰 구현 기준선 — 아래 내용은 2.5D 구현 완료를 뜻하지 않음:
- game/main.py와 core.py에 첫 프로토타입 구현, 지도는 core.py에 고정 배치
- visibility.py의 광선 경계와 화면 마스크로 손전등 340px·80도·건물 가림 구현, 타격 밀림 대신 제자리 0.4초 경직
- 소음 조사·건물 우회·도착 후 수색과 스태미나 달리기 추가, 좀비 체력 5타로 조정
- 걷기·좀비 90px/s, 달리기 135px/s, 스태미나 100·초당 25 소모·20 회복
- 주인공 탑뷰 아틀라스 적용, 맵·좀비는 임시 도형과 합성 효과음 5개 사용
- 기존 PPT 삽화는 콘셉트이며, 게임용 스프라이트나 모션 시트로 검수한 자료가 아님
- PC의 Python 3.13 설치 경로에서 pico2d 1.5.1 패키지와 이미지 회전·프레임 잘라 그리기·효과음 음량 함수의 소스 존재 확인
- 프로젝트 .venv 설치와 Windows 창 표시 확인, SDL 오디오 초기화·재생 호출 확인
- 사용자가 실제 키보드 Enter로 시작됨을 확인, 이동·공격 조작감과 출력 장치 청취는 별도 확인 필요, 손전등 암흑 마스크·건물 가림 구현
- Git은 planning/first-presentation 브랜치, 검증된 작업 단위마다 중간 커밋 관리
- 원격은 공개 https://github.com/yoon778/2D_project.git, 업로드 요청 시 작업 브랜치 푸시
- ddcba8a 기준선의 논리 테스트 39개·렌더 캡처 29개·자동 입력 1,342프레임·추적 자원 잔여 0개는 구 탑뷰 검증 기록
- 2.5D 투영·4방향 포즈·세운 스프라이트의 깊이·빛 노출은 미구현, 실제 조작감·장치 청취와 자동 검증도 구분

2026-11-03 현재 작업은 기획·개발 계획·발표 자료 갱신이며, 이 문서만으로 게임 코드나 에셋 제작을 시작하지 않음
아래 단계는 기존 실행본의 판정을 보존하면서 2.5D로 전환할 계획이며, 과거 진행 기록과 구분

## 2. 개발 방식

**작은 실행본을 만든 뒤 에셋 하나씩 교체**
에셋 전체 제작을 끝내고 게임을 연결하는 순서는 피함

1. 기존 지면 판정 위에 발점·투영·화면에서 지면으로의 조준 변환과 단순 맵 샘플 연결
2. 4방향 기본 포즈로 양손 장비·발점·깊이 확인
3. 짧은 4방향 보행·공격을 적용하고 스트레이프·후진 검수
4. 지면 빛과 세운 스프라이트 노출을 분리해 시야·벽 가림·소음·추격·거리 음향 재연결
5. 최소 맵에서 배달·승패·재시작 완주 후 필요한 리소스만 보완

매 단계에서 이전 단계의 배달·승패·재시작을 다시 확인
새 기능이 기존 흐름을 깨뜨리면 그 문제부터 수정

## 3. 최초 제작 규격과 공유 기준

아래 크기와 프레임 수는 제안값, 1~3단계 샘플 검수 후 조정 가능

| 항목 | 최초 제안 |
| --- | --- |
| 게임 화면 | 1280×720, 고정 화면 |
| 맵 논리 격자 | 40px 기준 32×18칸, 그림 타일 규격과는 분리 |
| 시점 | 고정 사선 3/4, 앞·옆·등과 다리가 보이는 2.5D |
| 캐릭터 원본 | 4방향 기본 포즈와 짧은 보행·공격, 투명 PNG와 발점 pivot 통일 |
| 화면 캐릭터 크기 | 발부터 머리까지 보이는 샘플로 결정, 구 정사각형 파트 크기를 현재 규격으로 사용하지 않음 |
| 조준과 그림 방향 | 연속 지면 조준각은 유지하고 그림만 4방향 선택, 한 방향 원본의 360도 회전 폐기 |
| 이동·깊이 | world(x,y)는 발 접지점, 발점 기준 투영과 깊이 정렬 |
| 충돌 크기 | 기존 지면 반경 플레이어 18px·좀비 20px를 초기값으로 유지, 새 그림 크기와 분리하고 튜닝 필요 시 합의 |
| 속도·공격 간격 | 시간 기준 처리, 화면 프레임 수에 종속시키지 않음 |
| 리소스 경로 | 프로젝트 기준 상대 경로, 다른 PC에서도 동일 |
| 에셋 기록 | assets/SOURCES.md에 생성·출처·사용 조건 기록 |

공유 규칙:
- world(x,y)는 왼쪽 아래 원점의 2D 지면 발 접지점, 충돌·거리·소음·깊이의 기준이며 시간은 초, 각도는 rad
- 지면→화면 투영과 마우스 화면→지면 조준 변환층을 짝으로 두고, 조준과 WASD 이동을 분리
- 세운 스프라이트는 발점 pivot과 방향별 같은 접지 기준을 사용하고, 발점 깊이에 따라 건물·캐릭터 앞뒤를 정렬
- 건물의 지면 footprint를 이동 충돌·길찾기·시야·공격 차단에 공유하되, 세워 그린 벽 실루엣과 충돌 도형은 분리
- 지면 빛 부채꼴·벽 가림과 세운 스프라이트 노출 pass를 분리해 허리·머리가 지면 마스크에 잘리지 않도록 검수
- 정교한 3D 조명·그림자·z축 물리는 추가하지 않음
- core.py의 기존 find_path와 건물 우회를 재사용하고 캐릭터 반경·모서리 충돌 확인, 이번 전환의 필수 범위에 길찾기 알고리즘 교체를 넣지 않음
- 소음 사건은 발생 시각·위치·반경·종류를 전달, 플레이어의 현재 위치를 계속 전달하지 않음
- 논리 판정과 그림을 분리, 이미지 교체가 공격 범위나 충돌 크기를 바꾸지 않도록 함
- 공격 애니메이션의 타격 순간과 실제 피해 판정은 하나의 공격 진행도를 공유
- 낮은 프레임에서도 타격 순간을 건너뛰어 피해가 사라지거나 중복되지 않도록 확인
- 전체 스프라이트 좌우 반전 금지, 각 방향에서 왼손 택배·오른손 방망이·가슴등 유지
- Game.start/restart/step/swing/interact/is_visible/pop_events와 Event(kind,x,y) 계약 유지 목표, 변경이 필요하면 지휘가 양쪽 영향을 먼저 합의

### S1. 환경과 실패 가능성이 큰 기술 확인

- 발 접지점의 지면→화면 투영·역변환과 마우스 화면→지면 조준 확인
- 임시 세운 스프라이트의 발점 pivot·4방향 선택·건물 앞뒤 깊이 확인

확인: 저장소 루트에서 .venv\Scripts\python.exe game\main.py 실행 후 직접 입력·화면·소리 확인

되돌림: 실험 코드는 별도 보관하고 확인된 최소 창 코드만 본 실행본에 유지

### S3. 4방향 기본 포즈 한 세트

배경: 정교한 아트나 8방향 제작 전에 4방향의 시점·발점·양손 장비부터 확인
선행: S1과 발점·방향 규격 합의

예정 산출물: assets/player/ 중심의 4방향 원본 PNG, 발점 기준 기록, assets/SOURCES.md
작업:
- 참고 이미지의 고정 사선 3/4 시점으로 플레이어 한 명과 좀비 한 종류 준비
- 앞·옆·등과 다리를 표현하는 4방향 기본 포즈, 같은 복장·색·비율·발 접지점 유지
- 왼손 택배·오른손 방망이·가슴등을 각 방향에서 확인, 전체 좌우 반전이나 한 방향 원본의 360도 회전으로 대체하지 않음
- 파트 분리 여부는 짧은 모션 샘플로 결정하고, 구 정수리 탑뷰 아틀라스를 새 시점의 완성본으로 취급하지 않음

## 6. 현재 파일 구조와 선택 후보

기능이 생기는 단계에서 필요한 파일만 추가, 미리 빈 구조를 전부 생성하지 않음
아래 목록은 game/ 내부 구조이며, 리소스는 main.py 위치를 기준으로 찾아 실행 위치가 바뀌어도 동작하도록 구성
현재 main.py·core.py·player_visual.py·visibility.py·spatial_audio.py 중심 구조를 유지하며, 이번 문서 전환은 대규모 구조 변경을 요구하지 않음
투영·조준 변환·발점 깊이·방향별 모션은 우선 화면 담당 범위에서 연결하고 Game API 변경은 지휘와 합의

- main.py: 시작점·게임 루프·화면 상태
- core.py: 이동·충돌·지도·배달·전투·좀비 감지와 길찾기의 기존 판정
- player_visual.py: 주인공 이미지·방향·모션·발점 표현
- visibility.py: 지면 시야·벽 가림과 빛 경계
- spatial_audio.py: 좀비 효과음 재생·거리별 음량
- requirements.txt: 기존 실행 의존성
- assets/player/, assets/audio/와 필요한 에셋 폴더: 실제 실행 리소스
- assets/SOURCES.md: AI 생성과 기존 자료의 출처·사용 조건
- tests/: 전투 중복 피해·벽 가림·감지 기억 등 중요한 논리 테스트만

player.py·zombie.py·world.py·combat.py·rendering.py·audio.py나 maps/level01.json은 실제 복잡도가 커졌을 때 합의할 분리 후보이며, 지금 만들거나 옮길 필수 산출물이 아님

문법 확인 예시: .venv\Scripts\python.exe -m compileall -q game/main.py game/core.py game/player_visual.py game/visibility.py game/spatial_audio.py
논리 테스트 예시: .venv\Scripts\python.exe -m unittest discover -s game/tests
위 명령은 해당 파일·가상환경·테스트를 만드는 실행 단계에서 사용, 현재 실행 완료를 뜻하지 않음

## 9. 단계 진행과 기록 규칙

- 각 단계의 시작 상태·확인 결과·다음 작업을 이 문서 끝에 짧게 기록
- 완료하지 않은 단계는 완료로 표시하지 않음
- 계획 변경 시 이유·영향받는 단계·완료 기준을 함께 갱신
- 단계가 커지면 더 작은 실행 가능한 작업으로 분리
- 지휘가 검증된 작업 단위마다 중간 커밋, 푸시는 업로드 요청 시에만 진행, 현재 작업 브랜치 이어서 사용
- 커밋 예: feat: 기본 이동과 택배 배달 구현 / fix: 벽 뒤 좀비 타격 오류 수정
- main 직접 커밋·푸시는 별도 사용자 요청 없이는 하지 않음

## 10. 사용할 스킬과 참고 자료

최초 계획 작성: session-defaults로 범위와 도구 선택, blueprint로 단계·의존관계·검증 기준 작성
실행 시 필요한 단계에서만 추가 스킬 적용:
- imagegen: 게임용 투명 PNG와 같은 원본 기반 파생 이미지
- python-patterns: Python 게임 코드가 복잡해질 때 필요한 부분만 적용
- diagnosing-bugs: 재현되는 오류가 생겼을 때 원인 확인
- verification-before-completion: 실행본의 완료 판단과 실제 검증

확인한 기술 근거:
- 설치된 pico2d 1.5.1 소스: Image.composite_draw, Image.clip_composite_draw, Wav.set_volume 존재
- [pico2d 배포 정보](https://pypi.org/project/pico2d/): 사용할 버전은 S1에서 수업 환경과 맞춰 확정
- [Red Blob Games 경로 탐색 설명](https://www.redblobgames.com/pathfinding/a-star/introduction.html): 작은 격자 BFS와 벽을 피하는 경로의 참고 자료

위 API 존재와 문서 확인은 프로젝트에서 실제 실행 검증을 통과했다는 의미가 아님
